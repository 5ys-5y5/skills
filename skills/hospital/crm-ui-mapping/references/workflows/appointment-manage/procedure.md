# 예약 관리

## 필수 선행조건

이 문서를 직접 요청받아도 먼저 상위 진입점의 매핑·호출 검증 절차를 따른다. [선행 검증](../../prerequisites.md)과 이 업무의 contract.json으로 mapping_valid를 확인한 후에만 업무를 시작하고, 실제 조작은 매번 action 검증의 ready 이후에 수행한다. 결과는 result.schema.json과 요청한 result_fields로 검증한다. 필수 XPath나 값이 없으면 매핑 정의로 돌아간다. 이 조건은 매핑 준비에 필요한 페이지 열기·로그인·화면 탐색을 막지 않는다. 스크립트 실행 환경이 없어도 문서의 동일 검증 항목을 직접 대조할 수 있다.

## 시작할 때

사용자가 제시한 페이지 또는 현재 작업 환경에서 안내한 CRM을 연다. 접속 정보·권한·인증 수단은 호출한 에이전트가 자신의 환경에서 확인해 사용한다. 이 스킬은 설정 파일의 위치, 키 이름, 비밀 저장 방식, 전용 API를 정하지 않는다.

이미 해당 병원·업무 계정으로 로그인되어 있으면 세션을 재사용한다. 로그인이나 추가 인증이 필요하면 현재 환경이 제공하는 수단을 따른다. 조작 전에 [업무 항목과 화면 요소 대응 기준](references/ui-mapping.md)을 읽고 요청 업무에 필요한 매핑을 확인한다. 요청에 꼭 필요한 정보만 부족할 때 확인한다.

현재 환경에 실제 제공된 브라우저 도구를 사용한다. 관찰한 페이지에서 대상을 식별하고 도구의 입력 규격에 맞춰 조작한다. 특정 도구 이름이나 자체 실행·검증 도구가 반드시 존재한다고 가정하지 않는다.

## 화면 매핑 확인

업무 조작은 검증을 통과한 profile의 XPath와 역할만 사용한다. 현재 환자·예약·청구·상담 상세에 해당하는 범위인지 실제 관찰로 확인하고 다음 조작을 action 검증한다. 화면이 달라지거나 대응이 없으면 임의 요소를 선택하지 않고 상위 진입점의 매핑 정의·검증 단계로 돌아간다.

첫 번째 일치 요소를 임의 선택하지 않는다. XPath가 유일해도 의미·소속 확인이 필요하다. 새 필드나 선행 버튼이 필요하면 먼저 profile에 등록하고 관계 검증을 통과시킨다. 요청에 필요한 입력값도 검증된 뒤에만 사용한다.

## 업무 처리

1. 요청 조치와 날짜·시간·진료과·의료진 조건을 확인한다. 시간대와 업무 범위는 현재 환경에서 확인한다. 공개 일정 조회에는 불필요한 환자 정보나 로그인을 요구하지 않는다.
2. 가능 시간·일정 조회라면 실제 필터를 적용하고 확인한 선택지를 답한다. 임의의 의료진이나 예약번호를 만들지 않는다.
3. 개인 예약 업무라면 환자를 특정한다. 변경·취소는 해당 환자의 예약 상세에서 예약번호·일시·의료진·현재 상태를 확인한다. 신규 환자 등록이 필요한 경우 이를 예약 요청에 포함된 조치로 단정하지 않는다.
4. 신규·변경은 화면의 실제 가용 시간과 선택지를 확인한다. 요청한 선택지가 없으면 가능한 대안을 안내한다. 신규 저장 전 환자·일시·의료진과 관련 진료 항목의 기존 예약을 확인한다.
5. 변경·취소 가능 여부는 현재 상태와 병원 운영 기준을 따른다. 이미 취소됐거나 종료된 예약을 같은 조치로 다시 처리하지 않는다. 필요한 취소 사유 등 필수 입력만 확인하고 요청한 예약 하나에 조치한다.
6. 저장 후 같은 예약의 상세를 다시 열어 환자·일시·의료진·상태를 대조한다. 저장 응답이 끊겼다면 먼저 존재 여부를 조회한다. 예약이 존재함을 확인한 것과 이번 시도로 생성됐음을 확인한 것은 구분한다.

완료 기준: 조회는 요청한 필터의 현재 결과를 확인했고, 쓰기는 대상 예약의 실제 상태가 요청과 일치한다. 개인 예약 처리 결과에는 확인 가능한 식별값과 일시·의료진을 답한다.
예: “다음 주 화요일 오후 가능한 시간을 알려주세요.” / “이 예약을 금요일 10시로 변경해 주세요.”

## 실패와 결과 불명

명확한 입력 오류는 해당 항목을 고쳐 다시 제출할 수 있다. 저장 성공 여부가 불명확하면 현재 상태를 조회한 뒤 판단하고 즉시 같은 조치를 반복하지 않는다. 확인할 수 없는 결과는 확인 불가로 설명한다.
